# قائمة جاهزية إطلاق Suly Plus

هذه القائمة تفصل بين ما يمكن التحقق منه آليًا وما يحتاج حسابات وخدمات حقيقية. لا تعتبر أي بند مكتملًا لمجرد نجاح البناء.

## 1. الأمان والبنية

- [x] استخدام Publishable Key فقط في المتصفح؛ لا تضع Service Role أو مفاتيح الدفع في متغيرات VITE.
- [x] عزل بيانات المتاجر بسياسات RLS في الجداول العامة.
- [x] إعادة احتساب أسعار الطلبات والكوبونات على الخادم.
- [x] التحقق من توقيع Paymob HMAC ومعالجة الأحداث المتكررة.
- [x] تحويل دالة تحديث حالة الطلب إلى SECURITY INVOKER، ومطابقة صلاحياتها مع سياسة UPDATE (owner/admin/manager).
- [ ] مراجعة تحذير Supabase بشأن RLS على private.checkout_rate_limits واعتماد سياسة مخصصة لدور الخدمة قبل الإطلاق.
- [ ] إجراء اختبار اختراق مستقل لمسارات IDOR وBOLA وRLS وStorage وواجهات Edge Functions.
- [ ] مراجعة سياسات النسخ الاحتياطي والاستعادة فعليًا، وتوثيق RPO/RTO.

## 2. التشغيل التجاري

- [x] إنشاء المتجر وإدارة المنتجات والتصنيفات.
- [x] إدارة الطلبات وسجل انتقال الحالة.
- [x] حركات المخزون والتسويات اليدوية.
- [x] إعداد الشحن والضريبة والكوبونات بحساب خادمي.
- [x] هوية المتجر الأساسية (الاسم والوصف والشعار) وبيانات التواصل.
- [x] دعوات أعضاء الفريق وإدارة الأدوار والإزالة مع سجل تدقيق؛ الإضافة والتعديل والإزالة محصورة بمالك المتجر وتخضع لحد أعضاء الخطة.
- [ ] مناطق الشحن وأسعارها حسب المحافظة/المدينة وشركة الشحن.
- [x] تقارير مبيعات حسب المنطقة الزمنية للمتجر وتصدير CSV؛ الأرقام مبنية على حالة الدفع المسجلة وتحتاج مطابقة مع البنك وبوابة الدفع.

## 3. تجربة العميل

- [x] واجهة متجر عامة، تصنيفات، تفاصيل المنتج، سلة، إتمام الطلب وتتبع الطلب.
- [x] صفحة حساب العميل لعرض آخر 50 طلبًا بعد تسجيل الدخول وتأكيد البريد المرتبط بالشراء؛ القراءة تتم من وظيفة خادمية لا تقبل بريدًا من المتصفح.
- [x] بحث وترتيب وقوائم صفحات المنتجات.
- [x] سجل طلبات خاص يعتمد على البريد المؤكد من Supabase Auth؛ الربط الحالي بالبريد وليس بمعرّف حساب محفوظ على الطلب.
- [ ] سياسات الإرجاع والاستبدال، وتدفق المرتجعات والاسترداد.
- [ ] رسائل البريد/SMS للطلب والدفع والشحن مع مزود معتمد.
- [ ] مراجعات المنتجات والمفضلة بعد وضع ضوابط منع الإساءة.

## 4. SaaS والفوترة

- [x] تأسيس جداول الخطط والاشتراكات والفواتير وإدارة الخطط وتعيين الاشتراكات يدويًا من لوحة Super Admin.
- [ ] اعتماد أسماء الخطط والأسعار وحدود الاستخدام وسياسة التجربة والإلغاء تجاريًا قبل نشر أي خطة.
- [ ] اختيار مزود فوترة/دفع اشتراكات مناسب للسوق والكيان القانوني وربط webhooks موثقة.
- [x] فرض حدود المنتجات وأعضاء الفريق والطلبات الشهرية داخل SQL والخادم؛ والتحقق من تاريخ بداية ونهاية الفترة ونهاية التجربة قبل السماح بالعمليات؛ وإظهار حالة الاشتراك الفعلية في لوحة التاجر.
- [x] إنشاء لوحة Super Admin محمية بصلاحية موثوقة من app_metadata، مع إجراءات إيقاف/تفعيل المتاجر وسجل تدقيق، وإدارة خطط وفواتير يدوية.
- [x] عدم منح صلاحية Super Admin من user_metadata القابل للتعديل من المستخدم.
- [ ] أتمتة التجديد والفشل في التحصيل والتعليق والإلغاء والإشعارات بعد اعتماد مزود فوترة.

## 5. الإطلاق والمراقبة

- [ ] اختبار E2E على بيئة staging بحسابين ومتجرين ومنتجات وطلبات حقيقية، بما في ذلك حدود الخطط والعمليات المتزامنة.
- [ ] اختبار Paymob Sandbox لجميع طرق الدفع المفعّلة، ثم اختبار إنتاج بمبالغ منخفضة.
- [ ] تحديد النطاق وHTTPS وDNS وإعدادات CORS وRedirect URLs.
- [ ] مراقبة أخطاء الواجهة والخادم والتنبيهات التشغيلية.
- [ ] اختبار ضغط واقعي وحدود المعدل وسلوك فشل الخدمات الخارجية.
- [ ] اختبار استعادة نسخة احتياطية، لا الاكتفاء بوجود النسخة.
- [ ] نشر سياسة الخصوصية والشروط وسياسة الإرجاع ومعلومات التاجر والضرائب بعد مراجعة قانونية محلية.

## ملاحظات لا يجوز تجاوزها

- قاعدة البيانات التي تمت مراجعتها كانت خالية من المستخدمين والمتاجر والمنتجات؛ لذلك لم يتم إثبات رحلة طلب كاملة من واجهة المتجر حتى الدفع والتسوية.
- لا توجد موافقة أو إعداد مؤكد لتسوية مدفوعات عدة متاجر عبر حساب Paymob واحد.
- نجاح CI يثبت فحوص TypeScript والاختبارات الحالية والبناء فقط، ولا يثبت الجاهزية التجارية أو القانونية.

## الإدارة المركزية وصلاحية Super Admin

أُضيفت لوحة أولية على المسار `/admin` ووظيفة `platform-admin-overview`. الوظيفة تتحقق من جلسة المستخدم من Auth، ثم تتحقق من `app_metadata.role = platform_admin` قبل استخدام Service Role لاسترجاع أعداد المنصة. لا تستخدم `user_metadata` لمنح هذه الصلاحية.

لمنح الصلاحية لحساب مسؤول موثوق، يجب أن يضبط مالك المشروع قيمة `app_metadata` من واجهة إدارة Supabase Auth أو عبر خادم إداري آمن، مثل:

```json
{ "role": "platform_admin" }
```

بعد تحديث app_metadata يجب تجديد جلسة المسؤول/رمز JWT. لا توجد واجهة عامة تسمح للمستخدم بمنح نفسه صلاحية الإدارة. لوحة الإدارة تشمل إيقاف/إعادة تفعيل المتاجر بسجل تدقيق، وإدارة الخطط وتعيين الاشتراكات والفواتير اليدوية. التحصيل والتجديد التلقائي غير مفعّلين.

## فحص اعتماديات npm

تمت ترقية `react-router-dom` إلى `7.18.5`، وأظهر آخر `npm audit` في CI النتيجة `0 vulnerabilities`. يجب إبقاء الفحص ضمن CI وإعادة تشغيله عند تحديث الاعتماديات.


## تقارير التاجر وإدارة الفريق

- تقارير المبيعات تقرأ بيانات الطلبات من SQL بصلاحيات المستدعي، وتسمح بها للمالك والمدير ومدير المتجر فقط، مع فترة قصوى 366 يومًا.
- إدارة الفريق متاحة لمالك المتجر فقط. الدعوات بالبريد تحتاج إعداد SMTP في Supabase، وتحتاج تجربة فعلية لبريد موثّق حتى يتم إثبات دورة الدعوة والقبول.
- حدود المنتجات والفريق تتحقق داخل قاعدة البيانات باستخدام triggers وأقفال على مستوى المتجر لمنع تجاوز الحدود بسبب عمليات متزامنة. كما تُراجع صلاحية فترة الاشتراك وتاريخ نهاية التجربة، وليس حقل الحالة وحده.
- حد الطلبات الشهرية يتحقق عند إنشاء طلب ضيف عبر دالة خادمية محمية؛ لا يوجد مسار عام مباشر لاستدعاء دوال إنشاء الطلبات.

## الاشتراكات والفوترة الحالية

- لوحة /admin/billing تدير الخطط، وتعيين الاشتراك للمتجر، وتغيير الحالة، وإنشاء الفواتير وتسجيل السداد يدويًا.
- صفحة /pricing تعرض الخطط المنشورة النشطة.
- لا يوجد تحصيل اشتراك آلي أو تجديد تلقائي أو مزود فوترة موصول حتى الآن. تسجيل الفاتورة كمدفوعة إجراء إداري يدوي وليس إثبات تحصيل مصرفي.
- لا توجد خطط افتراضية أو اشتراكات مخصصة في قاعدة البيانات؛ يجب على مدير المنصة اعتماد وإنشاء الخطط والأسعار أولًا.


تنبيه RLS المتبقي: Supabase ما زال يعرض تحذيرًا على الجدول الداخلي `private.checkout_rate_limits` لأن RLS غير مفعّل. فحص صلاحيات مباشر أظهر أن `anon` لا يملك `USAGE` على المخطط أو صلاحية قراءة/كتابة الجدول، وأن `authenticated` لا يملك صلاحيات قراءة/كتابة الجدول. مع ذلك، لا يزال تحذير RLS قائمًا ويجب اعتماد سياسة مناسبة للوظيفة الخادمية قبل الإطلاق. لا تفعّل RLS بلا سياسة واختبار مسار تحديد المعدل.

## حماية دعوات الفريق وسجل التدقيق

- إرسال دعوات الفريق محدود بعشر دعوات لكل متجر خلال أي 24 ساعة، ويُطبّق الحد داخل SQL بقفل على مستوى المتجر لمنع تجاوز الحد بالطلبات المتزامنة.
- تعرض واجهة الفريق الدعوات التي انتهى وقتها على أنها منتهية، حتى لو لم تُحدّث حالة الصف بعد.
- سجل تدقيق الفوترة يسجل إنشاء/تعديل/تفعيل/إيقاف الخطط، وتعيين الاشتراكات، وتغيير الحالة، وإنشاء الفواتير وتسجيل السداد اليدوي. قراءته وكتابته محصورتان في Service Role.
- CI يستخدم `npm install` لأن المستودع لا يحتوي على lockfile حاليًا، لكنه يفشل عند وجود ثغرات اعتماديات عالية أو حرجة، ويطبع تقريرًا لكل التحذيرات.


## سجل الطلبات لحساب العميل

- المسار `/account/orders` متاح من روابط الموقع العامة.
- يتطلب تسجيل الدخول وتأكيد البريد الإلكتروني؛ يستخدم الخادم البريد المؤكد من Auth ولا يقبل عنوانًا يحدده العميل في جسم الطلب.
- يعرض آخر 50 طلبًا بالمتاجر المختلفة مع المنتجات والمبالغ والحالات، ولا يعرض عنوان الشحن أو الهاتف أو رمز التتبع العام.
- يبقى اختبار رحلة حقيقية مع حساب مؤكد وطلب سابق ضروريًا قبل الإطلاق؛ قاعدة البيانات التي فُحصت لم تتضمن طلبات اختبار.
